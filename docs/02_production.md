# Часть II b. Проблемы и ограничения, возникающие в продакшене

В этом разделе — проблемы, которые становятся
критичными, когда RecSys обслуживает миллионы пользователей в реальном времени.

## Проблема 1. Latency (время отклика)

### Суть проблемы
В проде рекомендации должны приходить **за 100–200 мс**, иначе пользователь
уходит. В наших экспериментах `build_item_similarity` на 1682 фильма занял
~10–20 секунд. На каталоге в 1M товаров это будут **часы**, и это только
на этапе обучения — не на этапе выдачи.

### Как это проявляется
- **Обучение** модели: пересчёт матрицы похожести O(n²) — на больших данных
  не помещается в память
- **Инференс**: если считать рекомендации «на лету» для каждого запроса,
  это секунды на пользователя
- **Холодный старт сервиса**: после деплоя нужно прогреть кэш

### Как решать
1. **Pre-computed recommendations**: считать рекомендации офлайн (раз в час/день)
   и складывать в БД/кэш. При запросе — просто отдать готовое
2. **Approximate Nearest Neighbors (ANN)**: FAISS, Annoy, ScaNN —
   ищут похожие векторы за миллисекунды вместо O(n²)
3. **Кэширование** (Redis, Memcached): хранить топ-100 рекомендаций
   для активных пользователей
4. **Двухуровневая архитектура**:
   - **Retrieval** (быстро, грубо): достаём 100–500 кандидатов через ANN
   - **Ranking** (медленнее, точно): сортируем кандидатов тяжёлой моделью
5. **Асинхронность**: рекомендации не блокируют загрузку страницы,
   подгружаются отдельным запросом

### Недостатки решений
- **Pre-computed** - рекомендации устаревают. Пользователь посмотрел фильм,
  а система ещё час будет его рекомендовать
- **ANN** - теряем точность. Приближённый поиск может пропустить
  лучший фильм
- **Кэш** - нужно инвалидировать при изменениях, сложно поддерживать
- **Двухуровневая** - сложнее в разработке и поддержке

### Best practices
- **Netflix**: предвычисляет рекомендации для всех пользователей ночью,
  плюс онлайн-досчёт для свежих событий
- **YouTube**: использует двухуровневую систему (retrieval + ranking)
  с FAISS для поиска кандидатов
- **Amazon**: кэширует «similar items» для каждого товара, обновляет
  раз в несколько часов
- **Правило**: если пользователь ждёт > 200 мс, ты теряешь деньги

## Проблема 2. Масштабирование (Scalability)

### Суть проблемы
MovieLens 100k — игрушечный датасет. В реальном сервисе:
- **Пользователи**: миллионы (Netflix — 260M+)
- **Товары**: миллионы (Amazon — 350M+)
- **События**: миллиарды оценок и кликов в день

Матрица user × item становится **терабайтами**. Косинусная похожесть
на такой матрице невозможна.

### Как это проявляется
- **Память**: матрица 1M × 1M в float32 = 4 ТБ. Не влезает в RAM
- **Время обучения**: пересчёт похожести — дни, а не минуты
- **Инкрементальные обновления**: добавление нового пользователя
  требует пересчёта всей матрицы user_sim

### Как решать
1. **Разреженные матрицы** (scipy.sparse): храним только ненулевые
   значения. Экономия в 100–1000 раз
2. **Matrix Factorization**: SVD/ALS сжимает матрицу до скрытых факторов
   (например, 128 чисел на юзера и на товар)
3. **Шардирование**: разбить пользователей на шарды, считать
   рекомендации независимо
4. **Инкрементальные алгоритмы**: обновлять только изменившиеся части.
5. **GPU/распределённые вычисления**: Spark MLlib, Dask, Ray

### Недостатки решений
- **Sparse** - всё равно может не влезть в память на больших данных
- **MF** - теряем интерпретируемость, сложнее объяснить рекомендацию
- **Шардирование** - теряем «глобальную» похожесть между шардами
- **Инкрементальные** - сложно реализовать корректно
- **Spark** - дорого, требует инфраструктуры

### Best practices
- **Spotify**: использует Spark + ALS для обучения на миллиардах событий
- **Netflix**: обучает модели на GPU-кластере, хранит эмбеддинги
  в feature store
- **Amazon**: шардирует каталог по категориям, для каждой — своя модель
- **Правило**: не пытайся всё держать в памяти — используй распределённые
  вычисления и feature store

## Проблема 3. Data Drift (дрейф данных)

### Суть проблемы
Вкусы пользователей меняются: сезонность, тренды, новые релизы,
внешние события (пандемия, война). Модель, обученная полгода назад,
рекомендует «устаревшее».

### Как это проявляется
- **Сезонность**: летом люди смотрят блокбастеры, зимой — семейное кино
- **Тренды**: новый сериал взлетел — все хотят его смотреть
- **Внешние события**: во время карантина выросли просмотры
  документалок и стриминга
- **Изменение вкусов**: пользователь переключился с комедий на драмы

### Как решать
1. **Регулярное переобучение**: раз в день/неделю на свежих данных
2. **Онлайн-обучение**: модель обновляется на каждом событии (SGD)
3. **Мониторинг дрифта**: следить за изменением распределения оценок,
   метрик качества
4. **Feature engineering с временем**: учитывать день недели, час,
   сезон, «свежесть» фильма
5. **A/B-тесты**: проверять, что новая модель действительно лучше

### Недостатки решений
- **Регулярное переобучение** - дорого, нужно инфраструктура
- **Онлайн-обучение** - нестабильно, модель может «уплыть»
- **Мониторинг** - сложно настроить алерты, много ложных срабатываний
- **A/B-тесты** - занимают недели, стоят денег

### Best practices
- **Netflix**: переобучает модели ежедневно, использует «contextual bandits»
- **YouTube**: онлайн-обучение на потоке событий, переобучение раз в день
- **Spotify**: еженедельное переобучение + онлайн-докрутка
- **Правило**: модель — это не артефакт, а процесс. Её надо постоянно
  кормить свежими данными

## Проблема 4. Feedback Loop (петля обратной связи)

### Суть проблемы
Модель учится на данных, которые сама же и сгенерировала.
Если она показала пользователю только комедии, он смотрел только комедии,
и модель «убедилась», что он любит комедии. Замкнутый круг.

### Как это проявляется
- **Selection bias**: мы видим только то, что модель показала.
  Если фильм не рекомендовался — мы не знаем, понравился бы он
- **Exposure bias**: популярные фильмы получают больше показов,
  значит больше данных, значит ещё популярнее
- **Усиление предвзятости**: модель со временем становится
  всё более «уверенной» в узком наборе рекомендаций

### Как решать
1. **Random exploration**: с малой вероятностью показывать случайное
2. **Inverse Propensity Scoring (IPS)**: перевзвешивать данные
   с учётом вероятности показа
3. **Counterfactual evaluation**: оценивать модель на данных,
   которые она не генерировала
4. **Holdout-набор**: держать часть трафика на старой модели
   для сравнения
5. **Diversity constraints**: принудительно добавлять разнообразие

### Недостатки решений
- **Random exploration** - снижает CTR в краткосрочке
- **IPS** - требует знания вероятностей показа, сложно реализовать
- **Counterfactual** - нужны данные с рандомизацией
- **Holdout** - теряем часть трафика на «устаревшую» модель

### Best practices
- **YouTube**: использует «off-policy evaluation» для новых моделей
- **Netflix**: держит 5–10% трафика на exploration
- **Meta**: использует counterfactual learning для рекламы
- **Правило**: без exploration модель деградирует со временем

## Проблема 5. Мониторинг и алертинг

### Суть проблемы
Модель работает — но как понять, что она **сломалась**? Метрики в проде
могут упасть незаметно: утром CTR был 5%, вечером 3% — а ты узнаешь
об этом через неделю из отчёта.

### Как это проявляется
- **Тихие ошибки**: модель возвращает пустые рекомендации,
  а пользователь видит «популярное»
- **Деградация качества**: постепенное падение CTR на 0.1% в день
- **Технические сбои**: БД недоступна, кэш пустой, latency вырос
- **Data quality**: новые фильмы без жанров, битые оценки

### Как решать
1. **Мониторинг ML-метрик** (офлайн): Precision@K, Recall@K, Coverage —
   считать раз в день на holdout-выборке
2. **Мониторинг бизнес-метрик** (онлайн): CTR, Conversion Rate,
   Average Order Value, Retention — в реальном времени
3. **Технические метрики**: latency (p50, p95, p99), error rate,
   cache hit rate, QPS
4. **Data drift monitoring**: следить за распределением оценок,
   популярностью жанров, активностью пользователей
5. **Алерты**: если метрика упала на X% за Y часов — слать в Slack.
6. **Dashboard**: Grafana / Tableau с ключевыми метриками

### Недостатки решений
- **Много алертов** - alert fatigue, люди перестают реагировать
- **Мало алертов** - пропускаешь реальные проблемы
- **Офлайн-метрики** - не всегда коррелируют с онлайном
- **Dashboard** - никто не смотрит, если не настроены алерты

### Best practices
- **Netflix**: использует «A/B tests as a service», автоматические
  алерты на падение метрик
- **Uber**: Michelangelо — платформа для ML-мониторинга
- **Google**: SRE-подход: error budget, SLO/SLI для ML-сервисов
- **Правило**: если метрику нельзя измерить — её нельзя улучшить

## Проблема 6. A/B-тестирование

### Суть проблемы
Как понять, что новая модель **действительно лучше**? Офлайн-метрики
(Precision@K) не всегда коррелируют с бизнес-результатом (выручка,
retention). Нужны онлайн-эксперименты.

### Как это проявляется
- Новая модель лучше по NDCG@10, но хуже по CTR
- Новая модель лучше для активных юзеров, но хуже для новых
- Эффект есть, но он статистически незначим

### Как решать
1. **Классический A/B**: 50% трафика на контроль, 50% на тест
2. **Многоуровневый A/B**: тестировать несколько моделей одновременно
3. **Interleaving**: смешивать рекомендации двух моделей в одном списке,
   смотреть, что пользователь выберет
4. **Switchback-тесты**: для случаев, когда нельзя разделить трафик
   (например, для одного пользователя)
5. **Статистическая значимость**: считать p-value, доверительные интервалы,
   MDE (minimum detectable effect)

### Недостатки решений
- **A/B** - требует времени (недели), стоит денег
- **Многоуровневый** - сложнее анализировать, выше риск ошибок
- **Interleaving** - работает только для ranking-задач
- **Switchback** - сложно интерпретировать

### Best practices
- **Netflix**: запускает сотни A/B-тестов одновременно
- **Booking.com**: культура «test everything», 1000+ экспериментов в год
- **Airbnb**: использует «causal inference» для оценки эффектов
- **Правило**: не верь офлайн-метрикам, пока не проверил в A/B

| Проблема | Решение | Минус | Best practice |
|----------|---------|-------|---------------|
| Latency | Pre-compute, ANN, кэш | Устаревание | Netflix: офлайн + онлайн |
| Scaling | Sparse, MF, шардирование | Сложность | Spotify: Spark + ALS |
| Data drift | Переобучение, онлайн-обучение | Дорого, нестабильно | Netflix: ежедневно |
