# Часть III. Оценка RecSys в продакшене: ML и бизнес-метрики, мониторинг

Рекомендательная система оценивается двумя наборами метрик:

1. **ML-метрики** — офлайн, на исторических данных. Быстро, дёшево, но не всегда коррелируют с реальным успехом
2. **Бизнес-метрики** — онлайн, в проде. Медленно, дорого, но именно они показывают, приносит ли RecSys деньги

Главное правило: ML-метрики нужны для быстрой итерации, бизнес-метрики — для решения о раскатке. Если новая модель лучше по NDCG, но хуже по выручке, она не идёт в прод.

## 1. ML-метрики (офлайн)

### 1.1. Ranking-метрики

Эти метрики считались в `src/evaluate.py`.

| Метрика | Формула | Что показывает | Когда использовать |
|---------|---------|----------------|-------------------|
| Precision@K | hits / K | Доля релевантных в топ-K | Когда важна точность выдачи |
| Recall@K | hits / \|relevant\| | Какую долю релевантных нашли | Когда важно ничего не пропустить |
| NDCG@K | DCG / IDCG | Учитывает порядок в списке | Стандарт для ranking |
| MAP@K | среднее Precision по всем K | Усредняет Precision на всех позициях | Когда важен порядок |
| MRR | 1 / rank первого релевантного | Насколько высоко первый релевантный | Для поиска, Q&A |
| Hit Rate@K | 1, если есть хоть один релевантный | Простая бинарная метрика | Быстрая проверка |

### 1.2. Метрики разнообразия и покрытия

| Метрика | Что показывает | Зачем |
|---------|----------------|-------|
| Coverage | Доля каталога, которую модель рекомендует | Борьба с popularity bias |
| Diversity | Насколько разные фильмы в топе | Борьба с filter bubble |
| Novelty | Насколько «непопулярные» фильмы в топе | Борьба с «одним и тем же» |
| Serendipity | Насколько неожиданные, но релевантные | Баланс «приятного» и «полезного» |

### 1.3. Метрики качества ранжирования

| Метрика | Что показывает |
|---------|----------------|
| AUC | Способность разделять релевантное и нерелевантное |
| LogLoss | Качество вероятностных предсказаний |
| Calibration | Соответствие предсказанных вероятностей реальным |

### 1.4. Результаты проекта

Пример таблицы из `reports/metrics.csv`:

| Модель | Precision@10 | Recall@10 | NDCG@10 | Coverage |
|--------|--------------|-----------|---------|----------|
| Popularity | 0.0706 | 0.0483 | 0.0708 | 0.0117 |
| Content-based | 0.0203 | 0.0193 | 0.0265 | 0.2614 |
| Item-CF | 0.0006 | 0.0014 | 0.0019 | 0.1389 |
| User-CF | 0.0104 | 0.0136 | 0.0142 | 0.3171 |

Выводы:
- Popularity побеждает по ranking-метрикам на этом датасете — из-за сильного смещения MovieLens в сторону популярных фильмов
- User-CF даёт максимальный Coverage (31.7%) — рекомендует разнообразнее, но в ущерб точности
- Item-CF — самый слабый результат, причина в высокой разреженности матрицы (6.3% заполнения)
- Content-based — средний результат, жанры оказались слишком грубым признаком

## 2. Бизнес-метрики (онлайн)

Офлайн-метрики не отвечают на главный вопрос: зарабатывает ли компания больше денег. Для этого нужны онлайн-метрики.

### 2.1. Вовлечённость (Engagement)

| Метрика | Что показывает | Как считать |
|---------|----------------|-------------|
| CTR (Click-Through Rate) | Доля кликов по рекомендациям | clicks / impressions |
| Watch Rate | Доля просмотров после клика | views / clicks |
| Session Length | Длина сессии | среднее время на сайте |
| DAU/MAU | Активность | daily active / monthly active |
| Recommendation CTR | CTR именно блока рекомендаций | clicks_rec / impressions_rec |

### 2.2. Конверсия (Conversion)

| Метрика | Что показывает |
|---------|----------------|
| Conversion Rate | Доля покупок после рекомендации |
| Add-to-Cart Rate | Доля добавлений в корзину |
| Average Order Value (AOV) | Средний чек |
| Revenue per User | Выручка на пользователя |
| Revenue from RecSys | Доля выручки, пришедшая из рекомендаций |

### 2.3. Удержание (Retention)

| Метрика | Что показывает |
|---------|----------------|
| Day-1 / Day-7 / Day-30 Retention | Возвращается ли пользователь |
| Churn Rate | Доля ушедших |
| Lifetime Value (LTV) | Пожизненная ценность пользователя |
| Repeat Purchase Rate | Доля повторных покупок |

### 2.4. Специфичные для RecSys

| Метрика | Что показывает |
|---------|----------------|
| Catalog Coverage Online | Сколько товаров реально продаётся |
| Long-tail Revenue | Доля выручки от нишевых товаров |
| New Item Success Rate | Как быстро новые товары находят аудиторию |
| Diversity of Purchases | Насколько разнообразны покупки |

### 2.5. Связь ML и бизнес-метрик

| ML-метрика | Бизнес-метрика | Корреляция |
|------------|----------------|------------|
| NDCG@10 | CTR | Высокая |
| Recall@10 | Conversion Rate | Средняя |
| Coverage | Long-tail Revenue | Высокая |
| Diversity | Retention | Средняя |
| Novelty | Discovery Rate | Высокая |

Важно: корреляция не 100%. Бывает, что NDCG вырос, а CTR упал. Именно поэтому нужны A/B-тесты.

## 3. Мониторинг в продакшене

### 3.1. Что мониторить

**Технические метрики (real-time):**
- Latency: p50, p95, p99 (должно быть < 200 мс);
- QPS (queries per second);
- Error rate (должно быть < 0.1%);
- Cache hit rate (должно быть > 80%);
- CPU / Memory / Disk usage.

**ML-метрики (раз в день):**
- Precision@K, Recall@K, NDCG@K на holdout;
- Coverage, Diversity;
- Data drift (KL-divergence между train и prod);
- Prediction drift (изменение распределения скоров).

**Бизнес-метрики (real-time или раз в час):**
- CTR блока рекомендаций;
- Conversion Rate;
- Average Order Value;
- Revenue from RecSys;
- Session Length.

**Data quality (real-time):**
- % пропущенных значений;
- % новых фильмов без жанров;
- % аномальных оценок (например, все 5.0).

### 3.2. Инструменты

| Инструмент | Для чего |
|------------|----------|
| Prometheus + Grafana | Метрики, дашборды, алерты |
| ELK Stack | Логи |
| Evidently AI | Data drift, ML-мониторинг |
| WhyLabs | Мониторинг ML-моделей |
| Arize | Observability для ML |
| MLflow | Tracking экспериментов |
| Weights & Biases | Tracking и визуализация |

### 3.3. Алерты: что и когда

| Событие | Порог | Действие |
|---------|-------|----------|
| Latency p95 > 500 мс | 5 минут подряд | Page on-call |
| Error rate > 1% | 5 минут | Page on-call |
| CTR упал на 20% | за 1 час | Slack-алерт |
| NDCG упал на 10% | за день | Slack-алерт |
| Data drift > 0.3 | за день | Email команде |
| Пустые рекомендации > 5% | за 15 минут | Slack-алерт |

### 3.4. Принципы мониторинга

1. SLO/SLI: определить Service Level Objectives (например, «99% запросов < 200 мс») и измерять SLI
2. Error budget: если SLO нарушается — заморозить фичи, чинить
3. Alert fatigue: не больше 5–10 алертов в день на команду, иначе люди перестают реагировать
4. Runbook: для каждого алерта — инструкция, что делать
5. Post-mortem: после каждого инцидента — разбор, что улучшить

## 4. A/B-тестирование

### 4.1. Зачем нужно

Офлайн-метрики не отвечают на вопрос, стало ли лучше в реальности. A/B-тест — единственный способ доказать эффект.

### 4.2. Как проводить

1. Гипотеза: «Новая Item-CF модель увеличит CTR на 5%»
2. Метрика успеха: CTR блока рекомендаций
3. Размер выборки: считаем через power analysis (обычно нужно 10k+ пользователей на группу)
4. Разделение: 50% — контроль (старая модель), 50% — тест (новая)
5. Длительность: минимум 1–2 недели, чтобы покрыть weekly seasonality
6. Анализ: t-test, p-value < 0.05, доверительные интервалы
7. Решение: раскатываем, если эффект значим и положителен

### 4.3. Подводные камни

| Проблема | Что делать |
|----------|------------|
| Peeking — смотреть результаты до конца | Фиксировать длительность заранее |
| Simpson's paradox — эффект разный в подгруппах | Сегментировать анализ |
| Novelty effect — новый дизайн сначала нравится | Ждать 2+ недели |
| Network effects — пользователи влияют друг на друга | Использовать switchback-тесты |
| Multiple testing — много метрик | Bonferroni correction |

### 4.4. Что тестировать в RecSys

- Новую модель (Item-CF vs User-CF)
- Новый алгоритм ранжирования
- Новый дизайн блока рекомендаций
- Новые признаки (добавили жанры — стало лучше?)
- Новые пороги (min_votes=50 vs 100)

## 5. Итоговая схема оценки

Оценка RecSys в продакшене — это **многоуровневый процесс**:

1. **Офлайн** (быстро, дёшево): ML-метрики на holdout — Precision@K, Recall@K, NDCG@K, Coverage.
2. **Онлайн-пилот** (недели, дороже): A/B-тест на 5–10% трафика — CTR, Conversion, Retention.
3. **Полная раскатка** (месяцы): мониторинг всех метрик, алерты, регулярное переобучение.
4. **Обратная связь**: результаты бизнес-метрик → корректировка ML-метрик → новая итерация.

Без этого цикла RecSys быстро устаревает: вкусы меняются, дрейф данных накапливается, а модель, которая работала год назад, сегодня даёт нерелевантные рекомендации.
